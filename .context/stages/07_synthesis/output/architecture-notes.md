# Architecture notes (cross-stage)

Connections that no single stage owns. Each points at the stages it joins.

1. **A saved trip freezes its plan.** `saveTrip` stores both the config and the generated plan, and `loadTrip` copies that plan back without regenerating it. Later changes to the catalogs or engine rules therefore never reach already-saved trips. Joins `03_data/output/schema.md` + `state.md` and `04_interfaces/output/routes.md` (save rules).
2. **Climate has two writers.** The Step 1 climate chips edit `climate` directly, but `fetchWeather` overwrites it with the derived value on every location select and on every date change once a location is set. A manual climate choice can be lost by editing dates afterwards. Joins `04_interfaces/output/services.md` (derivation), `state.md` (`setTripDates` / `selectLocation` / `fetchWeather`) and `routes.md` (Step 1).
3. **Airline presets are display-only.** The engine always uses fixed 23 kg checked / 10 kg cabin capacities, and picking an airline doesn't change bag counts; only the Step 5 hint text uses the preset's weights. Joins `03_data/output/entities.md` and `04_interfaces/output/routes.md`.
4. **One rule lives in two places.** The "recommend insect repellent" condition (warm or rainy climate, or hiking) is implemented in `utils/healthEngine.ts` and re-implemented in `Step4HealthHygiene`. Change one and the other drifts. Joins `03_data/output/entities.md` and `routes.md`.
5. **Two "rainy" thresholds.** The weather adapter tags a trip `rainy` at ≥ 40% max rain probability, but `deriveClimateType` only picks the `rainy` climate at ≥ 50%. Joins `services.md` and `entities.md`.
6. **Stored data has no working version gate.** Saved trips embed the full `TripConfig`, `PackingPlan` and `WeatherProfile`, and `schemaVersion` is written but never read. Changing those types is a breaking change for data already on devices. Joins `03_data/output/schema.md` and `migrations.md`.
7. **The planned backend leans on today's catalogs.** The backend design seeds its `PackingItem` table by flattening this repo's `data/*` catalogs, expects the app to fetch items on boot, and keeps the quantity-formula engine client-side. Nothing in this repo fetches from such an API yet — the only network code is Open-Meteo. Joins `06_documentation/output/index.md` with `03_data/output/entities.md` and `services.md`.
8. **Theme changes reach every wizard screen.** `WizardStepLayout` wraps all five wizard steps and itself uses `AppButton`, `StepProgressBar`, `RADII` and `SPACING`, so edits there or to the theme files are the highest-leverage UI changes. Joins `05_ui/output/design-system.md` and `02_architecture/output/structure.md`.
9. **Test coverage follows the logic layers only.** Engines, store and weather adapters are tested; screens and components are not, so UI regressions (including the Lagoon & Sun restyle) have no automated net. Joins `02_architecture/output/structure.md` and `05_ui/output/design-system.md`.
